# Publish the library

This skill gets a release ready to publish. It does not publish.

## Ground rules

- **Never** run `publishToMavenCentral`, `publishAndReleaseToMavenCentral`, `publishAllPublicationsToMavenCentralRepository` or any other task that uploads to Maven Central. The user runs the upload after the hand-off.
- Never push, not the commit and not the tag. Pushing the tag starts the release workflow.
- Commit and tag only in step 9, after everything else passed, and only the release changes (version, README, CHANGELOG and anything regenerated in this run). Until then leave every change in the working tree.
- Never read `~/.gradle/gradle.properties` or the signing keys.
- If a step fails, stop and report the failure with the relevant output. Don't fix code to make a check pass unless the user asks you to.
- Run Gradle with `--console=plain`. Run long builds in the background and wait for them to finish.
- Keep a task list with one item per step below.

Shell snippets use Git Bash syntax and run from the repository root.

## Project facts

- Group and version are set in the root `gradle.properties` (`GROUP`, `VERSION_NAME`). All published modules share them.
- A published module is any module whose build file applies `alias(libs.plugins.mavenPublish)`. Find them with `git grep -l "libs.plugins.mavenPublish" -- '*/build.gradle.kts'`. Each one sets its artifact ID with `coordinates(artifactId = ...)`.
  - Right now the published modules are `:strata:gesture:draggable` (`gesture-draggable`) and `:strata:layout:animated` (`layout-animated`, `AnimatedColumn`). Each has a `*-baselineprofile` sibling.
  - A library module under `strata/` without the plugin is unpublished. Its build file says so in a comment. It still counts as a component for the README (step 7).
  - A new published module needs `mavenPublish` with `coordinates`, the `group` line, `abiValidation()`, committed ABI dumps, a `*-baselineprofile` sibling listed in `settings.gradle.kts`, and a `baselineProfile` block with a package filter. Copy them from an existing module.
- Every published module commits its ABI dumps under `<module>/api/`: `android/*.api` for the JVM ABI and `*.klib.api` for the iOS klib ABI. `checkKotlinAbi` fails when the code no longer matches the dumps. `updateKotlinAbi` rewrites them.
- A published module ships a baseline profile at `<module>/src/androidMain/generated/baselineProfiles/baseline-prof.txt`. The profile is generated by the module's `*-baselineprofile` sibling, which drives the demo app (`:androidApp`) on a connected device.
  - The profile filter is a prefix match on the package. Keep the demo's packages from starting with a library package (`animated` and `animatedcolumn` collided), or demo classes end up in the profile. Check with the grep in step 4.
  - The generators find the demo screens by text. A node that UiAutomator doesn't see, like the floating button of the task list, is tapped by position.
- Releases are tagged with the plain version, like `0.2.0`, without a `v`. The release workflow starts on a pushed tag and checks the version, the README snippets and the changelog (`.github/scripts/check-release-version.sh`), so step 7 must satisfy that script. Versions released before the tags existed are reconstructed from Maven Central (step 2).

## 1. Pre-flight: clean, synced master

```bash
git fetch origin
git branch --show-current            # must be master
git status --porcelain               # must be empty
git rev-list --count HEAD..origin/master   # must be 0 (not behind)
git rev-list --count origin/master..HEAD   # unpushed commits
```

- If you're not on `master`, or the working tree isn't clean, or the branch is behind `origin/master`, stop and tell the user.
- If there are unpushed commits, list them with `git log --oneline origin/master..HEAD`. Ask whether to go on, because the release would contain code that isn't on GitHub.

## 2. Published versions and the release baseline

For each published artifact ID, read what Maven Central already has. The KMP root artifact is the one without a platform suffix:

```bash
curl -s https://repo1.maven.org/maven2/dev/leonp/strata/gesture-draggable/maven-metadata.xml
```

- **HTTP 404 (nothing published yet):** this is the first release. Skip the ABI comparison in step 3. Keep the current `VERSION_NAME` without any `-SNAPSHOT` suffix as the release version, and still confirm it in step 6.
- **Versions listed:** let `L` be the highest version in `<versions>`. `maven-metadata.xml` can lag a new release by up to an hour. Also check the current `VERSION_NAME` directly with `curl -s -o /dev/null -w "%{http_code}" .../<version>/gesture-draggable-<version>.pom`. If it returns 200, that version is taken.

Next, find the baseline commit `BASE`, the commit `L` was published from. If the tag `L` exists (`git rev-parse -q --verify "refs/tags/$L^{commit}"`), `BASE` is that commit. Otherwise take the publish time from the POM's `Last-Modified` header. Then find the newest commit before that time whose `gradle.properties` has `VERSION_NAME=L`:

```bash
T=$(curl -sI "https://repo1.maven.org/maven2/dev/leonp/strata/gesture-draggable/$L/gesture-draggable-$L.pom" \
  | tr -d '\r' | sed -n 's/^[Ll]ast-[Mm]odified: //p')
for c in $(git rev-list --before="$T" HEAD); do
  git show "$c:gradle.properties" | tr -d '\r' | grep -qx "VERSION_NAME=$L" && { echo "$c"; break; }
done
```

Report `BASE` with its subject and date. If no commit matches, ask the user which commit `L` was released from.

List what changed in the published modules since then with `git log --oneline BASE..HEAD -- <published module dirs>`. If nothing changed, tell the user there is nothing to release and ask whether to stop.

## 3. ABI check

1. Check that the committed dumps match the code:
   ```bash
   ./gradlew checkKotlinAbi --console=plain
   ```
   If this fails, the public API changed but nobody updated the dump. Stop and show the reported diff. Run `./gradlew updateKotlinAbi` only if the user confirms that the API change is intended. Then review the new dump together with step 3.2. Uncommitted changes are expected at this point.

2. Compare the dumps with the last release. Skip this on the first release.
   ```bash
   git diff BASE -- ':(glob)**/api/**'
   git diff --stat --diff-filter=D BASE -- ':(glob)**/api/**'   # deleted dumps = removed module or target
   ```
   Classify the result:
   - **Breaking:** a declaration line was removed or changed (a `-` line), a dump file or a klib `// Targets:` entry was removed, or the klib `// Library unique name` changed. Kotlin ABI is stricter than source compatibility. Adding a parameter, even one with a default value, changes the signature. So does removing a default value, which removes the `$default` overload. A member added to a public interface, or an abstract member added to a public non-sealed class, also breaks existing implementations, even though it only shows up as a `+` line.
   - **Additive:** only new declarations (`+` lines).
   - **None:** the dumps are identical.

   Summarize every breaking change in one line each. You need that summary for the version choice and the CHANGELOG.

## 4. Baseline profiles

For each published module, decide whether its profile is stale. The example is for `draggable`, repeat it with the paths of every other published module:

```bash
MODULE=strata/gesture/draggable
PROFILE=$MODULE/src/androidMain/generated/baselineProfiles/baseline-prof.txt
LAST=$(git log -1 --format=%H -- "$PROFILE")   # empty if the module has no profile yet
git log --oneline ${LAST:+"$LAST"..}HEAD -- \
  $MODULE/src $MODULE/build.gradle.kts \
  $MODULE-baselineprofile demo androidApp gradle/libs.versions.toml \
  ":(exclude)$PROFILE"
```

- If the module has no profile file yet, it is missing, not stale. Generate it, or ask the user to ship without one.
- If no commits are listed, the profile is current. Say so and move on.
- If commits are listed, look at what they change. A commit that only touches KDoc, comments or unrelated demo text doesn't make the profile stale. Code changes in the library, changes to the generator, changes to the demo screens the generator drives, and Kotlin or Compose version bumps all do. If you're unsure, regenerate.

To regenerate:

1. Run `adb devices`. The generator needs an emulator or device in `device` state, on API 33+ or a rooted API 28+ image. If there isn't one, ask the user to start one. The user can also explicitly choose to ship the stale profile instead. Note that choice in the final report.
2. Run `./gradlew <module>:generateBaselineProfile --console=plain`, for example `:strata:gesture:draggable`.
3. Check the result:
   - The profile still contains library rules: `grep -c "dev/leonp/strata/<package>" "$PROFILE"` is not 0, with `draggable` or `animated` as the package.
   - Nothing outside the filtered package was pulled in.
   - `git status` shows no unexpected new files under `generated/`.

   Report the size of the profile diff with `git diff --stat`.

## 5. Full verification

```bash
./gradlew build --console=plain
```

This runs:
- detekt
- `checkKotlinAbi`
- iOS klib compilation
- all tests (when there are any)
- lint of the demo app
- the minified R8 release build of the demo app (`:androidApp:assembleRelease`)

On Windows, the iOS test and link tasks can't run. Report them as not covered.

If a device is still connected, also do a quick smoke test of the R8 build. It catches missing keep rules that the compiler can't catch:

```bash
./gradlew :androidApp:installRelease --console=plain
adb logcat -b crash -c
adb shell am start -W -n dev.leonp.strata/.MainActivity
sleep 5
adb shell pidof dev.leonp.strata   # must print a pid
adb logcat -d -b crash             # must be empty
```

## 6. Choose the version

Work out the proposed version from `L` and the ABI result in step 3:

| `L` | Breaking | Additive | None (fixes, profile, docs) |
| --- | --- | --- | --- |
| below 1.0 | minor + 1, patch 0 | patch + 1 | patch + 1 |
| 1.0 or higher | major + 1 | minor + 1 | patch + 1 |

- **First release:** propose the current `VERSION_NAME` without `-SNAPSHOT`.
- If `VERSION_NAME` already holds an unpublished version that differs from the proposal, show both.

Before writing anything, confirm with `AskUserQuestion`. Make the proposal the recommended option, and put the ABI classification and the list of breaking changes in its description.

## 7. Raise the version and update the docs

- `gradle.properties`: set `VERSION_NAME=<new>`.
- `README.md`: replace the version in every `dev.leonp.strata:<artifactId>:<version>` dependency snippet.
- `CHANGELOG.md`: create it if it doesn't exist, following the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format with a short header. Add a `## [<new>] - <YYYY-MM-DD>` section at the top. Use only the subsections that apply: `### Breaking`, `### Added`, `### Changed`, `### Fixed`.
  - Write the entries from `git log BASE..HEAD` of the published modules and from the ABI summary.
  - Write for library users. Describe what changed for them, not the commit history. Leave out internal-only commits.
  - For the first release, write one `### Added` section listing the public components in the API dump.
  - Check the previous release section against `git log`: a line that describes something added after that release was published is wrong. Move it to the new section.
- `.github/scripts/check-release-version.sh <new> master` passes for everything but the "tagged commit is on master" check, which only passes once the release commit is pushed. Run it and report anything else it flags.

### README coverage

Do this on every release, not only the first. A new component must be in the README in the same release that ships it, or while it is still unpublished.

1. List the components: the public composables and state classes in the API dumps of the published modules, and the public API (`public fun`, `public class`) of every unpublished library module under `strata/`. Compare them with `git diff BASE..HEAD --stat -- strata ':(exclude)*/api/*'` to find the new ones.
2. For each component, the README needs all of these:
   - a row in the **Components** table
   - a section under **Usage** with a short, correct example (copy the shape from the demo module, don't invent parameters)
   - a row in the **Project structure** table, when it lives in a module that is not listed yet
   - the feature list, if it adds a capability the list doesn't mention
3. New public members of an existing component, like a new method on a state class, get a short example in that component's usage section.
4. A component from an unpublished module is documented as **not published yet**, with a note that it is not part of the published artifact. Don't add a dependency snippet for it, because the release check compares every `dev.leonp.strata:` snippet in the README with the tag.
5. If the README has such a component, ask with `AskUserQuestion` whether it should ship in this release. If yes, the module first needs `alias(libs.plugins.mavenPublish)` with `coordinates(...)`, `abiValidation()` and committed API dumps, and possibly a baseline profile. Stop and tell the user what is missing instead of doing it silently. If no, keep it documented as unpublished.
6. Check the demo-app description in the README still matches the demo module.

## 8. Local publish dry run

```bash
./gradlew :strata:gesture:draggable:publishToMavenLocal :strata:layout:animated:publishToMavenLocal --console=plain
```

`signAllPublications()` signs even local publications. Excluding the `sign*` tasks with `-x` doesn't help, because the publication still expects the `.asc` files.

If the run fails with `no configured signatory`, the machine has no signing key configured. Rerun with a throwaway key that is valid for one day and lives in a temporary keyring. In the report, tell the user that their real key isn't set up here, so the upload would fail until it is.

```bash
export GNUPGHOME="$(mktemp -d)"
gpg --batch --quiet --passphrase dryrun --quick-gen-key "Strata dry run <dry-run@invalid>" ed25519 sign 1d
export ORG_GRADLE_PROJECT_signingInMemoryKey="$(gpg --batch --quiet --pinentry-mode loopback --passphrase dryrun --armor --export-secret-keys)"
export ORG_GRADLE_PROJECT_signingInMemoryKeyPassword=dryrun
./gradlew :strata:gesture:draggable:publishToMavenLocal :strata:layout:animated:publishToMavenLocal --console=plain
rm -rf "$GNUPGHOME"
```

Run all of it in one shell call. The exports don't persist between calls.

Check the output under `~/.m2/repository/dev/leonp/strata/` for the new version:

- Every publication is there: the root artifact, `-android`, `-iosarm64` and `-iossimulatorarm64`. Each has a `.pom` and a `.module` with the new version, a `-sources.jar` and a `-javadoc.jar`. Every file has an `.asc` signature next to it.
- The root `.module` points at the platform variants with the new version.
- The POMs carry name, description, URL, license, SCM and developer info, and no dependency on a `-SNAPSHOT` version (`grep -il snapshot`).
- The Android AAR contains the baseline profile: `unzip -l <aar> | grep baseline-prof.txt`.
- The iOS publications contain their `.klib`.

These artifacts stay in `~/.m2`. Mention that in the report, because a consumer project with `mavenLocal()` would pick them up.

## 9. Report and hand-off

Report briefly:

- the new version and the reason for it (ABI classification)
- the baseline commit `BASE`
- whether the profile was regenerated, kept, or knowingly left stale
- what the build covered and what it didn't (iOS tests on Windows, the smoke test if no device was connected)
- whether the dry run was signed with the user's key or a throwaway key
- the changed files

Then commit and tag, after everything above passed. If a step failed or was left open, stop before this and say so.

```bash
git add gradle.properties README.md CHANGELOG.md   # plus anything regenerated in this run, never unrelated changes
git commit -m "Release <new>"
git tag -a <new> -m "Release <new>"   # only on master, see below
```

- Tag only when the commit is on `master`. On a release branch that is merged through a pull request, the merge creates a new commit, and a tag on the branch commit would fail the release check. Then skip the tag, and tell the user to tag the merged `master` commit.
- If the tag exists already, stop and tell the user. Never move or delete a tag.
- Check `git status --porcelain` is empty and `git show --stat HEAD` lists only the release files.

Finally tell the user what's left. Show each command in its own `bash` block, and say that nothing has been pushed:

1. Push the commit, and merge it into `master` first if the release was prepared on another branch.
2. Push the tag. The release workflow verifies it, builds and uploads to Maven Central, with the secrets of the `maven-central` GitHub environment:
   ```bash
   git push origin <new>
   ```
3. Release the upload by hand from the Central Portal, because the workflow only uploads and validates. Switch the workflow to `publishAndReleaseToMavenCentral` to release right away.

Publishing from the machine instead needs `mavenCentralUsername`, `mavenCentralPassword` and the in-memory signing key in `~/.gradle/gradle.properties`. That is the user's call, not this skill's.
